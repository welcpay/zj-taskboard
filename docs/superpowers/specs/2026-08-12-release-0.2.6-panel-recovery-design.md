# Release 0.2.6 Panel Recovery Design

## Goal

Make the embedded Taskboard panel recover automatically when the local daemon is temporarily unavailable during an App or PKG upgrade. Users must not need to click `重新启动` after `127.0.0.1:47823` becomes healthy again.

## Confirmed Root Cause

The corrected 0.2.5 PKG installed successfully at 11:32, registered `/Applications/Codex Taskboard.app`, reconciled the versioned runtime, and left the launchd daemon healthy on `127.0.0.1:47823`.

During the daemon replacement window, the Codex injector attempted to prepare the embedded frame. The host binding or frame-ready handshake failed, and `prepareTaskboard` rendered a terminal error state. The injector retained no recovery loop, so the panel stayed on `任务面板服务未就绪` after the daemon had recovered. Repeated launcher diagnostics showed new blob frames that never reached `frameReady`, while the daemon health endpoint was already serving version 0.2.5.

## Recovery Behavior

The injector owns one recovery controller for the currently open panel generation. It starts only after `prepareTaskboard` fails while the panel remains active.

Recovery uses bounded exponential delays of 500 ms, 1 s, 2 s, 4 s, then 5 s for later attempts. It stops after 60 seconds. There is never more than one pending timer or one in-flight recovery attempt.

Each attempt performs the same authenticated host `ensure` operation used by a normal panel open. A successful ensure does not reuse the failed blob document. It clears the failed frame state, creates a new iframe with a new capability and challenge, loads a cache-busted Taskboard document, waits for the frame-ready handshake, then restores the captured Codex host context.

The recovery controller is canceled when:

- The panel closes or navigation returns to native Codex content.
- A newer `openGeneration` replaces the current attempt.
- The injection is destroyed or replaced by a newer source hash.
- Recovery succeeds.

Failures from stale generations must not replace the visible state of a newer panel open.

## User Experience

While recovery is active, the panel shows `正在恢复任务面板…` and does not require user action. The existing frame remains hidden because its document may contain a stale origin connection or failed bootstrap state.

After 60 seconds, the panel shows a final error with the most specific available host error. The action label becomes `立即重试`, because it retries the panel connection rather than restarting the resident daemon or the desktop App. Clicking it begins a fresh open generation and a fresh bounded recovery window.

No notification, modal, or repeated macOS permission prompt is introduced.

## Daemon and Installer Boundaries

The daemon remains independent of Codex and the desktop App, managed by the existing per-user LaunchAgent with `KeepAlive` and fixed port 47823. This release does not add another watchdog or service.

The 0.2.6 PKG retains the 0.2.5 installer corrections:

- Install the App only at `/Applications/Codex Taskboard.app`.
- Set `BundleIsRelocatable=false` and use `RootRelativeBundlePath`.
- Stop the old launcher before replacement.
- Open the installed App by its full path.
- Verify the daemon health response reports the installed version.

Application Support data, SQLite databases, attachments, Team Server profiles, Keychain tokens, and the previous runtime used for rollback remain preserved.

## Version and Artifacts

The next version is 0.2.6. The version must remain aligned in `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json`.

The local delivery directory is `dist/local-release-0.2.6` and contains:

- Universal macOS DMG.
- Universal macOS PKG.
- Universal App ZIP.
- Release notes.
- Release metadata.
- SHA-256 manifest.

Without a production Developer ID identity and notarization credentials, local artifacts remain ad-hoc or unsigned as appropriate. The release notes must state that limitation instead of presenting them as public production installers.

## Test Strategy

Injector contract tests must prove:

- A failed open schedules automatic recovery.
- Only one recovery timer and attempt can exist.
- Delay growth is bounded.
- Recovery creates a fresh cache-busted iframe rather than reusing the failed document.
- Success cancels recovery and displays the frame.
- Close, destroy, and a newer generation cancel stale recovery.
- The terminal action says `立即重试` and starts a fresh generation.

Release tests must prove:

- Every version source reports 0.2.6.
- The PKG component remains non-relocatable.
- The postinstall script launches the App by path and verifies daemon version 0.2.6.
- DMG, PKG, App ZIP, metadata, notes, and checksum manifest agree on version and hashes.

The final verification includes targeted injector and installer tests, the full Node test suite, TypeScript checking, the production Web build, Rust `cargo check`, App architecture and code-sign verification, DMG verification, expanded PKG inspection, and SHA-256 verification.

## Acceptance Criteria

- During a daemon stop and restart, an already open embedded panel changes to recovery state and returns automatically without a click.
- A failed or stale iframe is replaced and reaches `frameReady` after daemon recovery.
- Closing the panel stops all recovery work.
- A daemon that remains unavailable produces a useful final error after 60 seconds and offers `立即重试`.
- The daemon stays alive when Codex or the desktop App closes.
- Upgrading from 0.2.5 preserves local data and installs the App at `/Applications`.
- The generated 0.2.6 PKG is non-relocatable and the complete local artifact set passes verification.
